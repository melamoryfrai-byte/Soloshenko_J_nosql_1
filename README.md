## Відповіді на теоретичні питання частини 1

### 1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско?

Поля, що описують аудіо-властивості композиції (`danceability`, `energy`, `tempo`, `valence`, `loudness` та інші), були згруповані у вкладений об’єкт `audio_features`. Такий підхід дозволяє логічно об’єднати пов’язані характеристики та зробити структуру документа більш впорядкованою.

Використання вкладеного об’єкта також спрощує подальший аналіз даних і написання запитів до аудіо-характеристик. Наприклад:

```javascript
{ "audio_features.danceability": { $gte: 0.7 } }
```

Крім того, така структура краще відповідає документно-орієнтованій моделі MongoDB, де вкладені об’єкти використовуються для представлення логічно пов’язаних даних.

---

### 2. Чому виконавці зберігаються як масив, а не як рядок?

Поле `artists` було перетворено з текстового рядка на масив, оскільки один музичний трек може мати кількох виконавців одночасно.

Наприклад, у сирому датасеті значення могло виглядати так:

```text
Ingrid Michaelson;ZAYN
```

Після трансформації:

```javascript
artists: ["Ingrid Michaelson", "ZAYN"]
```

Зберігання виконавців у вигляді масиву є більш природним для документно-орієнтованої моделі MongoDB та дозволяє ефективніше виконувати пошук, фільтрацію й агрегацію.

Також це спрощує використання оператора `$unwind`, який дає можливість аналізувати статистику окремо для кожного виконавця.

---

### 3. Що таке `$out` і чим він відрізняється від `$merge`?

Оператор `$out` використовується для збереження результату Aggregation Pipeline у нову або вже існуючу колекцію MongoDB. Після виконання pipeline цільова колекція повністю перезаписується новими даними.

У цьому проєкті `$out` застосовується для створення фінальної колекції `tracks` на основі сирої колекції `tracks_raw`.

На відміну від `$out`, оператор `$merge` працює більш гнучко та дозволяє:
- оновлювати існуючі документи;
- додавати нові документи;
- об’єднувати результати з уже наявними даними.

Таким чином:

- `$out` доцільно використовувати для повного перестворення колекції;
- `$merge` краще підходить для часткового оновлення або інкрементального завантаження даних.

У цьому завданні використання `$out` є доречним, оскільки фінальна структура `tracks` створюється заново після кожного запуску трансформації.

## Відповіді на теоретичні питання частини 2

### 1. Для чого використовується інструкція `$unwind`?

Оператор `$unwind` використовується для розгортання масиву на кілька окремих документів. Після застосування `$unwind` кожен елемент масиву обробляється як окремий документ у pipeline.

У цьому проєкті `$unwind` використовується для поля `artists`, оскільки один трек може містити декілька виконавців:

```javascript
artists: ["Rauw Alejandro", "Lyanno", "Brray"]
```

Після виконання:

```javascript
{ $unwind: "$artists" }
```

MongoDB створює окремий документ для кожного виконавця. Це дозволяє коректно виконувати групування та обчислювати статистику для окремих артистів.

Без `$unwind` групування виконувалося б для всього масиву як одного значення.

---

### 2. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?

`$stdDevPop` та `$stdDevSamp` використовуються для обчислення стандартного відхилення, однак вони базуються на різних статистичних припущеннях.

`$stdDevPop` застосовується тоді, коли аналізується вся генеральна сукупність даних. У цьому випадку дисперсія обчислюється з діленням на `N`.

`$stdDevSamp` використовується для вибірки з більшої сукупності та застосовує поправку Бесселя, тобто ділення на `N - 1`.

У цьому проєкті використовується `$stdDevPop`, оскільки аналізуються всі треки, що присутні у датасеті для кожного жанру.

## Відповіді на теоретичні питання частини 3

### 1. Як зміниться результат, якщо змінити мінімальну кількість треків для виконавця?

Якщо зменшити мінімальний поріг кількості треків до `1`, у результат можуть потрапити виконавці лише з одним популярним треком. У такому випадку середня популярність буде формуватися на основі одного документа, що робить результат менш надійним.

Якщо ж збільшити поріг, наприклад до `50`, у вибірці залишаться лише виконавці з великою кількістю треків. Це підвищує статистичну стабільність середнього значення, однак значно зменшує кількість виконавців у результаті.

Таким чином:
- низький поріг дає ширшу вибірку, але менш стабільні результати;
- високий поріг забезпечує більш надійну статистику, але звужує вибірку.

---

### 2. Чи зміниться результат, якщо знизити мінімальну кількість треків у жанрі?

У цьому датасеті майже всі жанри містять приблизно однакову кількість треків — близько `1000`. Тому зміна порогу з `100` до `50` практично не вплине на результат агрегації.

У реальних менш збалансованих датасетах така зміна могла б додати жанри з невеликою кількістю треків, однак середні значення для таких категорій були б менш статистично надійними.

## Відповіді на теоретичні питання частини 4

### 1. Що змінилося в `executionStats` після створення індексу?

Після створення індексів MongoDB перестала використовувати повне сканування колекції (`COLLSCAN`) та перейшла до використання індексного сканування (`IXSCAN`).

Це дозволило:
- суттєво зменшити кількість переглянутих документів;
- скоротити час виконання запитів;
- зменшити навантаження на систему.

Також у статистиці виконання з’явилося поле `totalKeysExamined`, яке показує кількість переглянутих індексних ключів.

Для covered query значення `totalDocsExamined` стало рівним `0`, що означає відсутність звернення до самої колекції.

---

### 2. Чому порядок полів у compound index важливий?

MongoDB використовує compound index зліва направо, тому порядок полів безпосередньо впливає на ефективність виконання запиту.

Зазвичай на початку індексу розміщуються:
1. equality-поля;
2. поля для сортування;
3. поля з range-фільтрами.

У цьому проєкті для першого запиту був створений індекс:

```javascript
{
  track_genre: 1,
  "audio_features.danceability": 1,
  popularity: -1
}
```

Поле `track_genre` використовується для точного фільтра, `danceability` — для діапазонного пошуку, а `popularity` — для сортування результатів.

Правильний порядок полів дозволяє MongoDB ефективніше використовувати індекс і зменшувати кількість операцій під час виконання запиту.

---

### 3. Чому початковий запит не був covered query?

Початковий запит не був covered query, оскільки MongoDB повинна була зчитувати повні документи з колекції.

Навіть при використанні індексу в плані виконання залишалася стадія `FETCH`, оскільки без проєкції MongoDB повертає всі поля документа.

Після додавання проєкції:

```javascript
{
  _id: 0,
  track_genre: 1,
  popularity: 1
}
```

усі необхідні поля почали братися безпосередньо з індексу. У результаті запит став covered query, що підтверджується:
- появою стадії `PROJECTION_COVERED`;
- значенням `totalDocsExamined: 0`.
